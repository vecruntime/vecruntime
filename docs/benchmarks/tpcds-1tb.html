Apache Spark vs VecRuntime vs DataFusion Comet on TPC-DS 1 TB

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. Apache DataFusion Comet offloads the same operators to a native Rust engine. This page compares both against plain Apache Spark on the TPC-DS 1 TB workload on Amazon EKS, all three on identical hardware, data and Spark settings.

Benchmark infrastructure

Methodology. Spark and VecRuntime ran one after another in one cluster session on 2026-10-08, on the same nine nodes, each alone on the cluster, over the same S3 data with the same Spark settings; Comet 1.0.0 is its leg of the 2026-10-03 session on the same node type. Each query ran once after the plan was compiled; the time is the wall-clock of the query's execution as the runner measures it.

Where each engine wins

The scan-bound queries are VecRuntime's, on its own Parquet reader: q88 5.4 s against Spark's 153.2 and Comet's 83.0; q90 4.4 against 38.9 and 27.8; q9 14.5 against 104.1 and 52.0; q28 27.6 against 120.2 and 69.2. So are the heavy joins: q95 10.5 against 179.9 and 54.6; q93 16.9 against 86.1 and 76.9; q23b 85.5 against 221.2 and 133.2; q64 25.6 against 65.1 and 54.7. Comet leads on q49 (38.0 s against VecRuntime's 59.4, the bloom filter's build wait of #660), the heavy aggregates (q4 51.4 against 54.6), q65, q44, q16 and q18. VecRuntime's losses to Spark are q49 (59.4 s against 45.3) and q18 (6.2 against 5.9).

Notes

  • Every engine returned Spark's row counts on every query, and Spark's checksums on every query except q65, whose result has ties that every engine orders differently.
  • Spark and VecRuntime ran on 2026-10-08 in one cluster session on the same nine nodes, one after another, each alone on the cluster. The Comet column is Comet 1.0.0's leg of the 2026-10-03 session (same image settings, S3A settings and node type, another availability zone, without the 64 MB shuffled-hash-join threshold); a Comet leg in the 2026-10-08 session was stopped after 13 queries. S3 throughput varies between sessions, so the Comet comparison crosses sessions.
  • In the 2026-10-08 session Spark's scan-bound queries spent longer waiting on S3 than on 2026-10-03 at the same CPU time (q88 94.3 -> 153.2 s, q9 76.9 -> 104.1 s): Spark's total is 3,132 s against 2,963 s then. VecRuntime's reader, which reads the next files and row groups ahead, was stable within 1% across two runs that day.
  • The 64 MB shuffled-hash-join threshold moves Spark's own plans: sort-merge joins become shuffled hash joins in q93, q23a/b, q64 and q50 (faster) and in q95's web_sales self-join (179.9 s against 98.4 s without it).
  • Comet is the 1.0.0 release from Maven Central. The S3A settings, ACCP and compact object headers are the benchmark launcher's defaults since #566 and #578 and apply to all engines.
  • AQE is at its defaults for every engine apart from the shuffled-hash-join threshold.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests, the image and the data generation are in the benchmark runner's README: run-matrix.sh renders a SparkApplication per engine configuration (spark, vector-shuffle, comet, ...) and writes one JSON-lines result file per run; this page is rendered from three of them by benchmarks/scripts/render-benchmark-page.py.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. Times are the median of one measured iteration per query on the cluster described above; run-to-run variation on the heavy queries is a few percent.
