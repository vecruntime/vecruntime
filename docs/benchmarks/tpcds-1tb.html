Apache Spark vs VecRuntime vs DataFusion Comet on TPC-DS 1 TB

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. Apache DataFusion Comet offloads the same operators to a native Rust engine. This page compares both against plain Apache Spark on the TPC-DS 1 TB workload on Amazon EKS, all three on identical hardware, data and Spark settings.

TL;DR. Over the 103 TPC-DS queries at 1 TB, VecRuntime finished in 1,415 s against Spark's 2,963 s -- 2.09x, 52% less runtime, faster than Spark on 100 of 103 queries (best q49: 5.75x; largest regression q99: 7%). Comet finished in 1,964 s -- 1.51x, 34% less, faster on 96 of 103 (best q68: 2.81x; largest regression q43: 72%). Between the two, VecRuntime is faster on 74 of 103 queries and leads on the scan-bound queries and the heavy joins; Comet leads on q95, the heavy aggregates (q4, q11) and q18. Every engine returned Spark's results (q65: ties, ordered differently by every engine). Comet Native Scan + VecRuntime finished in 1,813 s -- 1.63x, 39% less, faster than Spark on 101 of 103 (best q29: 3.10x; largest regression q2: 26%), and faster than VecRuntime on its own reader on 29 of 103. Same operators and shuffle as VecRuntime, on Comet's Rust Parquet reader.

Benchmark infrastructure

Methodology. Spark, VecRuntime, Comet Native Scan + VecRuntime and Comet ran one after another in one cluster session on 2026-10-03, on the same nine nodes, each alone on the cluster, over the same S3 data with the same Spark settings; only the execution engine and its own memory split differ (every engine has 50 GB per executor; where it puts them follows where it allocates). Each query ran once after the plan was compiled; the time is the wall-clock of the query's execution as the runner measures it.

Where each engine wins

The scan-bound queries are VecRuntime's, on its own Parquet reader: q88 35.1 s against Spark's 94.3 and Comet's 83.0; q9 32.0 against 76.9 and 52.0; q28 60.7 against 97.4 and 69.2; q44 10.2 against 34.1 and 24.1; q90 9.6 against 27.2 and 27.8. So are the heavy joins: q23b 91.9 against 273.6 and 133.2; q64 24.5 against 88.5 and 54.7; q93 41.6 against 129.4 and 76.9. Comet Native Scan + VecRuntime (the same operators on Comet's Rust reader) finishes in 1,813 s against VecRuntime's 1,415 s on its own reader. Comet leads on q95 (27 s ahead), the heavy aggregates (q4 51.4 against VecRuntime's 62.1, q11 29.2 against 33.6), q65, q51, q96 and q18. VecRuntime's losses to Spark are q99 (9.0 s against 8.4, the join-chain gather of #603), q96 (15.5 against 14.6) and q12 (2.3 against 2.1).

Notes

  • Every engine returned Spark's row counts on every query, and Spark's checksums on every query except q65, whose result has ties that every engine orders differently.
  • The four legs ran on 2026-10-03 in one cluster session on the same nine nodes, one after another (Spark, VecRuntime, Comet Native Scan + VecRuntime, Comet), each alone on the cluster. S3 throughput varies between sessions, so only legs from one session are compared.
  • VecRuntime runs on its own Parquet reader (spark.vecruntime.scan.nativeParquet.enabled, #559), the default since #609: pages decoded in Java straight into the Arrow buffers its operators read, with the next files and row groups of each split read ahead on background threads.
  • Every engine ran with spark.locality.wait=0 (#608). Against the 2026-10-02 run, which kept Spark's 3 s wait, Spark went from 3,099 to 2,963 s, VecRuntime from 1,542 to 1,415 s (with #604 as well), Comet Native Scan + VecRuntime from 1,954 to 1,813 s and Comet from 1,999 to 1,964 s.
  • Comet is the 1.0.0 release from Maven Central. The S3A settings, ACCP and compact object headers are the benchmark launcher's defaults since #566 and #578 and apply to all four engines.
  • AQE is at its defaults for every engine.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests, the image and the data generation are in the benchmark runner's README: run-matrix.sh renders a SparkApplication per engine configuration (spark, vector-shuffle, comet, ...) and writes one JSON-lines result file per run; this page is rendered from three of them by benchmarks/scripts/render-benchmark-page.py.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. Times are the median of one measured iteration per query on the cluster described above; run-to-run variation on the heavy queries is a few percent.
