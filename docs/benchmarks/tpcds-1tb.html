Apache Spark vs VecRuntime vs DataFusion Comet on TPC-DS 1 TB

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. Apache DataFusion Comet offloads the same operators to a native Rust engine. This page compares both against plain Apache Spark on the TPC-DS 1 TB workload on Amazon EKS, all three on identical hardware, data and Spark settings.

Benchmark infrastructure

Methodology. Spark and VecRuntime ran one after another in one cluster session on 2026-10-10, on the same nine nodes, each alone on the cluster, over the same S3 data with the same Spark settings; Comet 1.0.0 is its leg of the 2026-10-03 session on the same node type. Each query ran once after the plan was compiled; the time is the wall-clock of the query's execution as the runner measures it.

Where each engine wins

The scan-bound queries are VecRuntime's, on its own Parquet reader: q88 5.5 s against Spark's 130.6 and Comet's 83.0; q90 4.6 against 34.8 and 27.8; q9 11.4 against 97.1 and 52.0; q28 27.1 against 111.8 and 69.2. So are the heavy joins: q95 10.6 against 170.6 and 54.6; q93 16.2 against 86.1 and 76.9; q23b 30.7 against 231.5 and 133.2; q64 26.8 against 61.7 and 54.7; and the heavy aggregates (q4 33.7 against 88.1 and 51.4). Comet leads on q47 (9.0 s against VecRuntime's 22.8) and q57 (4.9 against 11.1), on q44, q18, q65 and q34, and by fractions of a second on a set of short queries. VecRuntime's losses to Spark are q47 (22.8 s against 12.0), q57 (11.1 against 6.5) and q44 (35.7 against 35.0).

Notes

  • Every engine returned Spark's row counts on every query, and Spark's checksums on every query except q65, whose result has ties that every engine orders differently.
  • Spark and VecRuntime ran on 2026-10-10 in one cluster session on the same nine nodes, one after another, each alone on the cluster. The Comet column is Comet 1.0.0's leg of the 2026-10-03 session (same image settings, S3A settings and node type, another availability zone, without the 64 MB shuffled-hash-join threshold). S3 throughput varies between sessions, so the Comet comparison crosses sessions.
  • Spark's total is 2,997 s on 2026-10-10, against 3,132 s on 2026-10-08 and 2,963 s on 2026-10-03: its scan-bound queries move with S3 throughput between sessions (q88 130.6 s on 2026-10-10, 153.2 s on 2026-10-08).
  • The 64 MB shuffled-hash-join threshold moves Spark's own plans: sort-merge joins become shuffled hash joins in q93, q23a/b, q64 and q50 (faster) and in q95's web_sales self-join (170.6 s against 98.4 s without it).
  • Comet is the 1.0.0 release from Maven Central. The S3A settings, ACCP and compact object headers are the benchmark launcher's defaults since #566 and #578 and apply to all engines.
  • AQE is at its defaults for every engine apart from the shuffled-hash-join threshold.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests, the image and the data generation are in the benchmark runner's README: run-matrix.sh renders a SparkApplication per engine configuration (spark, vector-shuffle, comet, ...) and writes one JSON-lines result file per run; this page is rendered from three of them by benchmarks/scripts/render-benchmark-page.py.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. Times are the median of one measured iteration per query on the cluster described above; run-to-run variation on the heavy queries is a few percent.
