Apache Spark vs VecRuntime vs DataFusion Comet on TPC-DS 1 TB

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. Apache DataFusion Comet offloads the same operators to a native Rust engine. This page compares both against plain Apache Spark on the TPC-DS 1 TB workload on Amazon EKS, all three on identical hardware, data and Spark settings.

TL;DR. Over the 103 TPC-DS queries at 1 TB, VecRuntime finished in 1,542 s against Spark's 3,099 s -- 2.01x, 50% less runtime, faster than Spark on 99 of 103 queries (best q5: 5.07x; largest regression q18: 52%). Comet finished in 1,999 s -- 1.55x, 35% less, faster on 97 of 103 (best q6: 3.06x; largest regression q72: 15%). Between the two, VecRuntime is faster on 61 of 103 queries and leads on the scan-bound queries and the heavy joins; Comet leads on the heavy aggregates (q4, q11, q24a/b, q67) and q18. Every engine returned Spark's results (q65: ties, ordered differently by every engine). Comet Native Scan + VecRuntime finished in 1,954 s -- 1.59x, 37% less, faster than Spark on 98 of 103 (best q29: 3.25x; largest regression q7: 75%), and faster than VecRuntime on its own reader on 27 of 103. Same operators and shuffle as VecRuntime, on Comet's Rust Parquet reader.

Benchmark infrastructure

Methodology. Spark, VecRuntime, Comet Native Scan + VecRuntime and Comet ran one after another in one cluster session on 2026-10-02, on the same nine nodes, each alone on the cluster, over the same S3 data with the same Spark settings; only the execution engine and its own memory split differ (every engine has 50 GB per executor; where it puts them follows where it allocates). Each query ran once after the plan was compiled; the time is the wall-clock of the query's execution as the runner measures it.

Where each engine wins

The scan-bound queries are now VecRuntime's, on its own Parquet reader: q88 35.0 s against Spark's 96.1 and Comet's 84.2; q9 30.6 against 73.2 and 50.5; q28 58.4 against 101.8 and 67.3; q44 9.6 against 34.8 and 22.0; q90 7.4 against 30.7 and 31.0. So are the heavy joins: q23b 104.0 against 288.2 and 138.1; q64 25.5 against 87.6 and 48.8; q93 51.9 against 129.2 and 72.2. Comet Native Scan + VecRuntime (the same operators on Comet's Rust reader) finishes in 1,954 s against VecRuntime's 1,542 s on its own reader, so the reader is now the faster one of the two. Comet leads on the heavy aggregates and a few mid-size queries: q4 57.1 against VecRuntime's 70.6, q11 30.5 against 38.6, q24a 79.2 against 93.7, q24b 74.8 against 90.9, q65 13.1 against 19.0, q18 4.5 against 12.1. VecRuntime's losses to Spark are q18 (12.1 s against 8.0, under investigation), q99 (10.0 against 8.4), q92 (1.9 against 1.6) and q12 (2.3 against 2.2).

Notes

  • Every engine returned Spark's row counts on every query, and Spark's checksums on every query except q65, whose result has ties that every engine orders differently.
  • The four legs ran on 2026-10-02 in one cluster session on the same nine nodes, one after another (Spark, VecRuntime, Comet Native Scan + VecRuntime, Comet), each alone on the cluster. S3 throughput varies between sessions, so only legs from one session are compared.
  • VecRuntime runs on its own Parquet reader here (spark.vecruntime.scan.nativeParquet.enabled=true, #559): pages decoded in Java straight into the Arrow buffers its operators read, with the next files and row groups of each split read ahead on background threads. The flag is off by default; the earlier runs on this page (docs/results.md) used Spark's reader.
  • Comet is the 1.0.0 release from Maven Central. The S3A settings, ACCP and compact object headers are the benchmark launcher's defaults since #566 and #578 and apply to all four engines.
  • AQE is at its defaults for every engine.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests, the image and the data generation are in the benchmark runner's README: run-matrix.sh renders a SparkApplication per engine configuration (spark, vector-shuffle, comet, ...) and writes one JSON-lines result file per run; this page is rendered from three of them by benchmarks/scripts/render-benchmark-page.py.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. Times are the median of one measured iteration per query on the cluster described above; run-to-run variation on the heavy queries is a few percent.
