VecRuntime vs Gluten + Velox vs DataFusion Comet on TPC-DS 3 TB, AWS Graviton4

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. awslabs data-on-eks publishes TPC-DS 3 TB results for two native engines, Gluten + Velox and DataFusion Comet, on twelve Graviton4 nodes. This page runs VecRuntime on the same generated data, the same instance type and count and the same executor layout, and sets its times against theirs.

Benchmark infrastructure

Methodology. The dataset was generated with data-on-eks's own generator image and arguments, and VecRuntime ran on the node type, node count and executor layout of their benchmark (23 executors x 5 cores, 58 GB each), at their 200 shuffle partitions. The run had the cluster to itself; each query ran once after the plan was compiled, and its time is the wall-clock of its execution as the runner measures it.

Test environment

ComponentConfiguration
DatasetTPC-DS scale factor 3000 (3 TB), Parquet on Amazon S3, generated with the data-on-eks generator image and arguments unchanged (103 query variants)
ClusterAmazon EKS; 12 x r8gd.12xlarge (48 vCPU AWS Graviton4, 384 GB, local NVMe as RAID0 for shuffle and spill), the data-on-eks benchmark's instance type and count
Executors23 executors x 5 cores x 58 GB each, as data-on-eks (Gluten / Comet: 20 GB heap + 6 GB overhead + 32 GB off-heap); VecRuntime: 35 GB heap + 23 GB overhead; driver 5 cores x 24 GB
StorageAmazon S3 through Hadoop 3.4.3 S3A with the Analytics Accelerator input stream

VecRuntime configuration

spark.plugins=io.vecruntime.spark.VectorPlugin
spark.shuffle.manager=org.apache.spark.sql.vecruntime.shuffle.VectorShuffleManager
spark.sql.shuffle.partitions=200   (data-on-eks's setting, Spark's default)
spark.sql.adaptive.enabled=true
spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold=64MB
spark.vecruntime.exec.strictFloatingPoint=false
spark.hadoop.fs.s3a.connection.maximum=1000, threads.max=256, max.total.tasks=128
Executors: -XX:+UseParallelGC -XX:ParallelGCThreads=5 (data-on-eks runs ParallelGC too); ACCP as the JCA provider
--add-modules=jdk.incubator.vector --enable-native-access=ALL-UNNAMED (driver and executors)

Notes

  • The Gluten and Comet numbers are data-on-eks's published results (the mean of their iterations); they were not re-run here. VecRuntime's are one measured iteration per query.
  • VecRuntime runs at data-on-eks's own setting, 200 shuffle partitions with AQE coalescing, so all three engines share the configuration.
  • At 200 partitions VecRuntime needs the larger overhead (35 GB + 23 GB): with 44 GB + 14 GB an executor exceeded its container in q93.
  • The engines run on different Spark lines: VecRuntime needs Spark 4.1+ and JDK 25, the data-on-eks Gluten and Comet runs are on Spark 3.5.8 and JDK 17.
  • There is no Apache Spark baseline at 3 TB, so result checksums are not compared against Spark here; VecRuntime's results match Spark's on the 1 TB runs and in the test suites.
  • The previous version of this page (2026-10-10, VecRuntime 0.0.7 + #690 + #691, at 900 and 200 partitions) is kept in benchmarks/results/tpcds-sf3000-doeks-2026-10-10/.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests and the image are in the benchmark runner's README; the image builds for arm64 on an arm64 node. run-matrix.sh writes one JSON-lines result file per run; this page is rendered from one of them and data-on-eks's two result CSVs by benchmarks/scripts/render-doeks-page.py. The 1 TB runs against Apache Spark are on the Graviton4 1 TB page.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. VecRuntime's times are one measured iteration per query; run-to-run variation on the heavy queries is a few percent.
