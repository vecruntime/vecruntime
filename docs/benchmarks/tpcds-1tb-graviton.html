Apache Spark vs VecRuntime on TPC-DS 1 TB, AWS Graviton4

VecRuntime runs Spark SQL's filters, projections, aggregates, sorts and joins on Arrow-layout batches with the Java Vector API -- on the JVM, no native code -- and moves batches between executors over its own Arrow Flight shuffle. This page compares it against plain Apache Spark on the TPC-DS 1 TB workload on Amazon EKS with AWS Graviton4 (arm64) nodes, and sets both against the published x86 run (which used a 128m advisory size and coalescePartitions.minPartitionNum=208; this run uses AQE's defaults) (#253).

TL;DR. On Graviton4, over the 103 TPC-DS queries at 1 TB, VecRuntime finished in 1,801 s against Spark's 2,207 s -- 1.23x, 18% less runtime (geometric mean 1.21x), faster than Spark on 77 of 103 queries (best q29: 3.34x; largest regression q18: 66%). On the x86 nodes the same comparison is 1.29x (geometric mean 1.24x): the lead carries over to arm64. Both engines run faster on Graviton4 than on the m5.4xlarge nodes -- Spark's time is 0.69 of its x86 time and VecRuntime's 0.71, per query (geometric mean). Row counts equal Spark's on 103 of 103 queries; checksums on every query except q65 (ties in the result, ordered differently by each engine).

Benchmark infrastructure

Methodology. The two engines ran one after another on the same nodes, each alone on the cluster, over the same S3 data with the same Spark settings; only the execution engine and its own memory split differ (every engine has 50 GB per executor). Each query ran once after the plan was compiled; the time is the wall-clock of the query's execution as the runner measures it.

Configuration

Common to both engines:

spark.sql.shuffle.partitions=300
# spark.sql.adaptive.advisoryPartitionSizeInBytes left at Spark's default (64 MB); no coalescePartitions.minPartitionNum
spark.eventLog.enabled=true

VecRuntime:

spark.plugins=io.vecruntime.spark.VectorPlugin
spark.shuffle.manager=org.apache.spark.sql.vector.shuffle.VectorShuffleManager
spark.vector.exec.strictFloatingPoint=false   # Comet's default too
spark.vector.shuffle.aqe.mapSizeScaling=true   # #514's default: AQE sees Spark-scale map output sizes
spark.vector.shuffle.aqe.sparkCompressionRatio=0   # #514's default: the uncompressed-bytes ratio
AOT class-data cache off
--add-modules=jdk.incubator.vector --enable-native-access=ALL-UNNAMED (driver and executors)

The arm64 platform

  • HotSpot on Graviton4: UseSVE=2, MaxVectorSize=16 -- the Vector API's species are 128 bits wide, as on NEON.
  • VecRuntime's platform probe picks its SVE paths: native compress (SVE COMPACT) for selection, and the broadcast-AND-compare lane masks, because VectorMask.fromLong is not intrinsified at 128-bit SVE on JDK 25 (#253, #484).
  • The native codecs (snappy, zstd, lz4) and Netty's epoll transport load their aarch64 libraries; neither architecture has libhadoop, as on x86.

Notes

  • Both engines returned the same row counts on every query and the same checksums on every query except q65, whose result has ties that each engine orders differently (q65's checksum also differs between two runs of the same engine).
  • Both legs ran on 2026-09-26, one after another on the same nodes, each alone on the cluster, with AQE's defaults: 300 shuffle partitions, the advisory partition size unset (64 MB), no coalescePartitions.minPartitionNum.
  • With AQE's defaults Spark runs faster than with the earlier page's 128m advisory size and minPartitionNum=208 (2,207 s against 2,696 s on 2026-09-25), so the lead over Spark is measured against the faster Spark.
  • VecRuntime reports its map output sizes to AQE on Spark's scale (#511, #514): its columnar shuffle is 1.6-4.3x smaller than Spark's for the same rows, and without the scaling AQE packed up to twice Spark's rows into a task -- q67's final aggregate spilled 115 GB and took 92 s; with it q67 takes 39 s and does not spill.
  • The x86 reference is the published run, with a 128m advisory size and minPartitionNum=208, so the architecture comparison below mixes two AQE settings; its VecRuntime also predates #514.

Running the benchmark

The cluster runner, the Spark-on-Kubernetes manifests, the image and the data generation are in the benchmark runner's README; on Graviton the image builds for arm64 on an arm64 node and the runs select the arm64 node group. run-matrix.sh writes one JSON-lines result file per run; this page is rendered from two of them, with the x86 page as the reference, by benchmarks/scripts/render-graviton-page.py.

TPC-DS is a benchmark of the Transaction Processing Performance Council; these results are not audited TPC results and are not comparable to published TPC-DS results. Times are one measured iteration per query on the cluster described above; run-to-run variation on the heavy queries is a few percent.
